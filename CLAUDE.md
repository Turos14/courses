# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A single-page French-language web app ("Mes Courses & Menus Collaboratifs") for managing recipes, planning a meal calendar, and generating shopping lists. It's a static site with no build step and no framework — plain HTML/CSS/JS loaded directly by the browser via `<script>` tags in `public/index.html`. The repo root additionally has an npm project (Playwright tests + a deploy-zip script) that wraps that static site; the site itself still has zero runtime dependencies.

## Running the app

Serve `public/` with any static file server and open it in a browser, e.g.:

```
npm run serve
```

(equivalent to `npx http-server ./public -p 4173`). Then visit `http://localhost:4173/`. Opening `public/index.html` directly via `file://` also works for most functionality but `navigator.clipboard` (used by the share link "Copier le lien" button) requires a secure context (http(s) or localhost).

There is no linter or formatter in this repo.

`.devcontainer/devcontainer.json` defines a Codespaces/VS Code Dev Containers environment (Node 20 image, `npm install` + `npx playwright install --with-deps chromium` on creation, port 4173 forwarded) for coding from the browser without a local setup.

## Testing

Playwright end-to-end tests drive the real static site in a real browser (no mocking, no DOM simulation) — see `tests/*.spec.js`, config in `playwright.config.js`.

```
npm install                      # first time
npx playwright install chromium  # first time, downloads the browser binary
npm test                         # runs the whole suite headlessly
npm run test:ui                  # interactive UI mode for debugging a single test
npx playwright test tests/dishes.spec.js   # run one file
npx playwright show-report                 # open the HTML report from the last run
```

`playwright.config.js` auto-starts `http-server` on `public/` (port 4173) before the run via `webServer`, so you don't need to serve the app manually. Each test gets a fresh browser context, so `localStorage` is empty at the start of every test — no manual cleanup needed. Use `browser.newContext()` inside a test (see `tests/share-import.spec.js`) when you need to simulate a *second*, independent device (e.g. testing the QR/import flow), since reusing `page`'s context would share the exporting device's `localStorage`.

**Gotchas:**
- Inactive `.view-section`s stay in the DOM (hidden via `display:none`, not removed), and dynamically-built modals/tab bars are re-rendered per view/open. Loose locators like `page.getByText('Ajouter un ingrédient')` or `page.locator('.modal-body')` can match more than one element (e.g. the dish-form's "Ajouter un ingrédient" button and the calendar's "Ajouter un ingrédient isolé" button both contain that substring; the static, hidden `#modal-share`/`#modal-import` also have class `.modal-body`) and throw a strict-mode violation. Prefer `page.getByRole('button', { name: '...', exact: true })`, scope the locator to a specific container/view, or exclude hidden overlays (`.modal-overlay:not(.hidden) .modal-body`).
- When a button has both visible text/emoji *and* an `aria-label`, the `aria-label` becomes its accessible name and **replaces** the visible text for `getByRole` matching — e.g. a button rendering `🛒 Liste de courses` with a differing `aria-label` must be matched by that `aria-label`, not the visible text.
- The calendar view is week-based, not month-based: locate a day by its weekday name (`page.locator('.week-day-card', { hasText: 'Lundi' })`), not by a day-of-month number — the displayed week (and therefore which numeric dates appear) depends on whatever "today" is when the test runs. See the `weekDayCard`/`mealSlot` helpers duplicated across `tests/calendar.spec.js`, `tests/shopping-list.spec.js`, `tests/persistence.spec.js`.

## Deployment

Two deployment paths exist side by side. **Manual** (e.g. for the self-hosted `apps.home.ithasu.org` portal): `npm run zip` (`scripts/zip.js`) zips the contents of `public/` (flattened, no wrapping folder) into a versioned `courses-v<version>.zip` (from `package.json`'s `version`) at the repo root, ready to upload wherever the static app is hosted. **Automatic** (GitHub Pages): `.github/workflows/deploy-pages.yml` deploys `public/` on every push to `main` (and on manual `workflow_dispatch`), via the standard `actions/configure-pages` + `actions/upload-pages-artifact` + `actions/deploy-pages` trio — requires the repo's Settings → Pages → Source to be set to "GitHub Actions" (one-time, not settable from the workflow file itself).

Every local CSS/JS/icon/manifest `<script>`/`<link>` tag in `public/index.html` carries a `?v=CACHE_VERSION_PLACEHOLDER` query string, so each deploy forces browsers — notably mobile Safari for sites added to the home screen — to refetch CSS/JS instead of serving a stale cached copy; the placeholder itself is a valid (if inert) query string, so local dev (`npm run serve`, Playwright's `webServer`) is unaffected without needing the substitution. Both deployment paths must keep performing this same substitution on their own copy of `index.html` (never on the committed file itself) rather than assuming the other one already did it: `zip.js` replaces it with a build timestamp when writing `index.html` into the zip; the Pages workflow replaces it with `${{ github.sha }}` via `sed` on the checked-out workspace copy before uploading the Pages artifact.

## Architecture

**Global mutable state, no framework, no modules.** All scripts are loaded as plain, non-module `<script>` tags in a fixed order (`public/index.html:213-223`) and communicate through variables/functions attached to `window`. There is no bundler and no import/export syntax — load order in `index.html` matters and must be preserved when adding new files.

Load order: `state.js` → `storage.js` → `navigation.js` → `modal.js` → `categories.js` → `editor.js` → `shoppingList.js` → `share.js` → `calendar.js` → `calendarShare.js` → `main.js`.

There used to also be a standalone "weekly shopping list" screen (pick dishes with a +/- counter, no calendar) — it's gone; the calendar (see below) is now the only way to plan meals and generate a shopping list. If you see references to `view-course-selection`, `js/courseSelection.js`, `window.selectedDishesCounts`, or a global `window.customIngredients` in old context/history, that's this removed flow — don't resurrect the pattern, extend the calendar instead.

- **`js/state.js`** — declares all global state on `window` (`dishes`, `viewHistory`, `editingDishId`, `shoppingListItems`, `shoppingListChecked`, `categories`, `activeCategoryFilter`, `activeMealPickerCategoryFilter`, `savedCalendars`, `activeCalendarId`) and the `viewTitles` map used for the header title.
- **`js/storage.js`** — `saveLocalData()` / `loadLocalData()` persist all state to `localStorage` (dishes/list under `*_v3` keys, categories/calendar-related state under `*_v1` keys — bump a suffix if that piece's data shape changes incompatibly). Every mutation elsewhere in the app is expected to call `saveLocalData()` immediately after changing state. `loadLocalData()` runs a few one-time cleanups on every load (cheap no-ops once the legacy data is gone): `migrateLegacyCalendarDraft()` — before multi-calendar support, there was a single global calendar draft (`mes_calendrier_assignations_v1` / `mes_calendrier_petitdej_v1`); non-empty data there is wrapped into a normal `window.savedCalendars` entry (made active) — `migrateLegacyCustomIngredients()` — before "ingrédients isolés" moved into the calendar, they lived in a single global `window.customIngredients`; any non-empty leftover is attached to the active (or most recent) calendar's `customIngredients` — `removeLegacyFavorites()`, which just deletes the `mes_favoris_v1` key now that the favorites feature is gone entirely (no replacement to migrate into, unlike the other two) — and `migrateCalendarBreakfastSelections()` — before breakfast became free items (see `js/calendar.js`), it was a selection of "petit-déjeuner"-typed dishes (`cal.breakfastSelection`, `{ dishId: count }`); each calendar without a `breakfastItems` array yet gets one built from its old selection (dish name looked up live, falling back to `cal.dishesSnapshot`), one calendar at a time — this one doesn't delete a separate top-level key (there isn't one; `breakfastSelection` is nested per-calendar) so the stale field is just left in place, unused, rather than actively stripped out. This convert-or-delete-on-load pattern (strip the top-level key when there is one) is the template for any future state shape migration or feature removal.

  **Do not break the localStorage format.** There is no migration mechanism: `loadLocalData()` just `JSON.parse`s whatever is stored under each key and assigns it straight to the corresponding `window` variable, with no schema validation or backfill for missing/renamed fields. Since this is the user's only copy of their data (no server, no sync), any incompatible change to a stored shape (renaming/removing a field like `n`/`q` on ingredients, changing an array to an object, etc.) will silently corrupt or lose existing users' recipes and lists on next load. If a shape must change, keep reads backward-compatible (e.g. default/derive missing fields) or bump the key suffix and handle the old key as a one-time migration rather than assuming a clean slate.
- **`js/navigation.js`** — single-page "view" router. Views are sibling `<div class="view-section">` elements in `index.html`, toggled via the `active` CSS class. `navigate(viewId)` pushes onto `window.viewHistory`; `goBack()` pops it. Entering a view triggers that view's render function (e.g. entering `view-editor` calls `renderEditorList()`) and re-renders `#header-actions` (view-specific buttons in the blue header bar, e.g. the editor's share/new-dish icons) via `renderHeaderActions()`. New views must be registered in `viewTitles` and wired into `navigate()`, `goBack()`, and `renderHeaderActions()` as needed. The header's left side (`.header-left`) holds two elements: a permanent portal link (`<a href="https://apps.home.ithasu.org/">`, always visible, external navigation — not part of `viewHistory`) and `#btn-back` (in-app back, toggled by `showView()` based on `viewHistory.length`) — don't conflate the two; the portal link never hides.
- **`js/modal.js`** — `showCustomModal(title, text, onConfirm, showCancel, confirmLabel, confirmColor)` builds a generic confirm/alert modal dynamically (replaces native `alert`/`confirm`). `confirmLabel`/`confirmColor` are optional and default to `'Supprimer'`/red, because historically every `showCancel: true` call was a delete confirmation — pass them explicitly for any other 2-button confirmation (e.g. `'Importer'`/green, `'Ouvrir'`/blue) so the button doesn't show a misleading red "Supprimer".
- **`js/categories.js`** — user-defined "tabs" (`window.categories`, each `{ id, name }`) for organizing dishes. `renderCategoryTabs(containerId, filterKey, renderListFn)` draws the tab bar; `filterKey` is the name of the `window.*` variable holding *that view's* active tab (`'activeCategoryFilter'` for the editor, `'activeMealPickerCategoryFilter'` for the calendar's midi/soir dish picker — each view keeps its own selected tab, they don't share state) and `renderListFn` is called on tab selection so the caller re-renders its filtered list. The calendar's breakfast section does *not* use category tabs — breakfast items aren't dishes, see `js/calendar.js`. `promptNameInput(title, confirmLabel, initialName, placeholder, onConfirm)` is a generic "ask for a name" modal (despite living in this file — it predates the calendar and was generalized rather than duplicated) reused by `promptAddCategory()`/`promptRenameCategory(cat, onDone)` here *and* by `js/calendar.js` for creating/renaming a calendar. `openManageCategoriesModal()` lists categories with rename/delete actions. Deleting a category clears `categoryId` on any dish that referenced it (and resets any view filter pointing at it) rather than deleting those dishes; renaming mutates `cat.name` in place, so dishes keep their association via `categoryId` (no migration needed). The `.category-tabs` CSS class (`public/css/style.css`) has both `overflow-x: auto` (so a long tab row scrolls horizontally instead of overflowing the modal/view, with a `mask-image` fade at the edges hinting it's scrollable) and `flex-shrink: 0` — the latter is load-bearing specifically inside `openMealDishPicker()`'s flex-column modal (`js/calendar.js`): setting only `overflow-x` makes the browser auto-compute `overflow-y` as `auto` too (per the CSS Overflow spec, one non-`visible` axis forces the other off `visible`), which strips this element's normal protection against being shrunk below its content height by the flex layout — with enough dishes making the sibling `#meal-picker-list` want more vertical space than fits, the tab bar would get squashed to a sliver instead of the list scrolling internally on its own. Don't remove `flex-shrink: 0` without re-verifying that scenario (many dishes, tab bar still full height).
- **`js/editor.js`** — CRUD for dishes/recipes (`window.dishes`), each with `{ id, name, ingredients: [{ n, q }], categoryId }`. Renders the editor list (filtered by `window.activeCategoryFilter` via the category tabs, then sorted alphabetically by name with `localeCompare(..., 'fr', { sensitivity: 'base' })` — display-only, doesn't mutate `window.dishes`' stored order) and the dish create/edit form. There is no dish "type" any more (an earlier `mealType: 'plat' | 'petit-dejeuner'` field, with a segmented-control picker in the form and a matching top-right switcher in the editor, was tried and then fully removed — see `js/calendar.js` below for why): every dish in the editor is just a dish, and every dish is available in the calendar's midi/soir picker. Breakfast planning is a separate, dish-independent concept.
- **`js/shoppingList.js`** — `window.buildShoppingListItems(dishCounts, customIngredientsList, dishLookup)` is the shared aggregation core (grouping/deduplicating by `name+qty`, case-insensitive, summing counts) used by the calendar's `generateCalendarShoppingList()` (in `calendar.js`) to populate `window.shoppingListItems`. `dishLookup` defaults to searching live `window.dishes`; the calendar instead passes `id => window.dishes.find(...) || cal.dishesSnapshot[id]` — live data first (freshest ingredients) falling back to the calendar's embedded snapshot for a dish that doesn't exist locally (an imported calendar's dish, or one since deleted). `customIngredientsList` entries are free items (`{ name, qty, count }`); their line in the final list's `origins` reads `originLabel || 'Ajout direct'` — the calendar tags breakfast items with `originLabel: 'Petit-déjeuner'` (see `js/calendar.js`) at call time (not stored on the item) so both "ingrédients isolés" and breakfast items share this single aggregation path while staying distinguishable in the final list. Don't reintroduce a separate copy of this aggregation logic for a new "generate list" flow — extend the shared function instead. `renderFinalList()` renders the final checklist view and tracks checked items in `window.shoppingListChecked` (a `Set` of item ids); `generateCalendarShoppingList()` clears this set first, so a freshly generated list always starts unchecked.
- **`js/share.js`** — exports all dishes as a base64-encoded JSON payload embedded in a `?import=...` URL query param, so recipes can be transferred between devices. `generateShareQRCode()` (bound to the editor's header 📤 button, `aria-label="Partager mes recettes"`) prefers `navigator.share()` (the OS share sheet — Mail, Messages, etc.) when available and `shareUrl.length` is within `NATIVE_SHARE_MAX_BYTES` (8000, a defensive margin — some browsers, notably Chrome/Android, kill the whole tab with a `RESULT_CODE_KILLED_BAD_MESSAGE` crash rather than cleanly rejecting an oversized `navigator.share()` call, so this size must be checked *before* calling it, not caught after); past that (or when the API isn't available at all, e.g. desktop), `showShareLinkModal()` is the fallback, rendering a QR code (via the `QRious` CDN script tag in `index.html`) plus a copyable link in `#modal-share`. A QR code separately caps out at 2953 bytes in byte mode at error-correction level `'L'` (the densest we use) — past that, **QRious does not throw**, it silently truncates the data, so the QR still looks fine and scans cleanly but decodes to a corrupted/truncated link. `showShareLinkModal()` checks `shareUrl.length` against that 2953-byte threshold itself and swaps in a warning message (`#share-qr-warning`) instead of calling `QRious` when it would overflow — never let `QRious` attempt to render data past that cap. Each exported dish carries its category *by name* (`c: categoryName || null`, resolved from `window.categories` at export time) rather than by id, since the importing device's category ids are unrelated to the exporter's — ids in the payload would be meaningless on the other end. `checkURLForImport()` runs on load and offers to merge imported dishes (skipping name-collisions case-insensitively); category resolution itself only happens in `confirmImportDishes()` (not at parse/preview time, so rejecting the import creates nothing): each dish's category name is matched case-insensitively against `window.categories`, reusing the existing category if found or creating one (`'cat-' + Date.now() + '-' + counter`, a counter suffix since several new categories can be created within the same millisecond in one import) if not. The base64 payload is `encodeURIComponent`-ed before being appended to the URL (a raw `+` in base64 output would otherwise be misread as a space by `URLSearchParams` on read) — `URLSearchParams.get()` decodes it back transparently, so the read side needs no matching change. Keep both the encode step and the native-share-first/QR-size-guard pattern on any new share-link flow that embeds base64 in a query param (`js/calendarShare.js` follows the same pattern). A share link doubles as a way to "install" the app pre-seeded with the current recipes: open the link in Safari, then "Add to Home Screen" from that page — the installed icon's launch URL is then permanently that `?import=...` link (iOS always re-navigates to the exact URL captured at Add-to-Home-Screen time, since standalone apps aren't live-synced with the browser's other tabs/windows). Because of that, `checkURLForImport()` tracks already-*resolved* `import` payload strings in `localStorage` (`mes_liens_import_vus_v1`, capped at the last 20, via `markImportLinkAsHandled()`) and silently skips re-showing the import modal for a payload already handled — without this, every single relaunch of such an installed icon would re-trigger the same import prompt forever, since `cleanURL()`'s `history.replaceState` only clears the *current session's* address bar, not what the icon replays next time. The payload is deliberately marked as handled *inside* `confirmImportDishes()`/`rejectImport()` (i.e. once the user actually acts on the modal), **not** inside `checkURLForImport()` at parse time — iOS Safari silently loads a page in the background (running its JS, `checkURLForImport()` included) to generate the preview thumbnail for a long-pressed link (Messages, Notes, …), with no human ever seeing the modal; marking the one-time-use link as handled that early would let that invisible preview-load permanently burn it before the user ever opens it for real, so the import modal would then never appear at all. `js/calendarShare.js`'s `checkURLForCalendarImport()` has the same guard (`mes_liens_import_calendrier_vus_v1`, marked inside the `showCustomModal` confirm callback) for the same reason.
- **`js/calendar.js`** — the meal calendar (`view-calendar`) — the app's only meal-planning/shopping-list-generation entry point, and the single screen for *all* calendars (there's no separate "list of calendars" screen — see below). There is no "draft": every entry in `window.savedCalendars` is directly, continuously editable, and `window.activeCalendarId` points at whichever one is currently open; `getActiveCalendar()` resolves it, and lazily backfills `customIngredients: []`/`breakfastItems: []` on calendars created before those fields existed. `window.openCalendarHome()` (wired to the home screen's "Calendrier" button) always lands on `view-calendar`, prompting to create the very first calendar only if none exist at all. `window.promptCreateCalendar(onCreated)` creates a new entry (`{ id, name, createdAt, origin: 'local', assignments: {}, breakfastItems: [], customIngredients: [], dishesSnapshot: {} }`), pushes it, makes it active, and persists.
  - **Switcher, not a separate list screen**: `renderCalendarSwitcher()` draws every calendar as a pill (reusing `.category-tab` styling) across the top of `view-calendar`, highlighting the active one; tapping a pill just sets `window.activeCalendarId` and re-renders — non-destructive, since there's no draft to lose. A trailing "+" pill calls `promptCreateCalendar`. Rename (pencil) and delete (trash, `confirmDeleteActiveCalendar()`) icons sit next to the active calendar's name and only ever act on it — there's intentionally no "delete/share a calendar without first switching to it"; switching is one tap, so this was judged an acceptable simplification over keeping a whole separate management screen.
  - **Week view, not a month grid**: `changeCalendarWeek(delta)`/`goToCurrentCalendarWeek()` (module-level `calendarViewWeekStart`, a Monday, not persisted) page by 7 days. `renderWeekDays(cal)` renders one card per day (`getMondayOfWeek`/`formatWeekRange`/`formatDateLong` are the date-math helpers) with two always-visible "☀️ Midi"/"🌙 Soir" slots showing the assigned dish name(s) directly as text — no click-to-reveal step. Tapping a slot calls `openMealDishPicker(dateKey, meal)` directly — its dish list is simply `window.dishes` (all of them; there's no dish subtype any more), narrowed by category tabs (its own transient filter `'activeMealPickerCategoryFilter'`, reset each open) — and writes the selection into `cal.assignments['YYYY-MM-DD'][meal]`. This replaced an earlier month-grid-with-a-dot-indicator design specifically because dish names weren't visible without an extra tap+modal.
  - **Breakfast is not a dish-selection any more.** An earlier design gave dishes a `mealType: 'plat' | 'petit-dejeuner'` field (picker in the dish form, plus a matching switcher in the editor splitting it into two lists) and let you *select* petit-déjeuner-typed dishes into `cal.breakfastSelection` (`{ dishId: count }`) — including auto-adding a newly-saved breakfast dish into every non-frozen calendar. All of that was tried and then fully removed: breakfast is now just free-text items, structurally and behaviorally identical to "ingrédients isolés" (see below) — a dish and a breakfast item are now two completely separate, unrelated concepts. `cal.breakfastSelection` may still exist as a stale, unused field on old stored calendars (see `js/storage.js`'s `migrateCalendarBreakfastSelections()`, which converts it to `breakfastItems` on load) — don't resurrect the dish-based pattern if you see it referenced in old context/history.
  - **"Items libres"**: `cal.customIngredients` ("Ingrédients isolés") and `cal.breakfastItems` ("Petits-déjeuners de la semaine" — a *single list for the whole calendar*, not per-day, deliberately: "on choisit autant de trucs que l'on veut" once, not repeated per day) are two arrays sharing the exact same item shape (`{ id, name, qty, hasQty, count }`) and the exact same CRUD/render behavior — neither is tied to a dish or a category. Rather than duplicate that logic per list, `FREE_ITEM_LISTS` is a config map (`{ customIngredients: { containerId, idPrefix: 'cust', placeholder }, breakfastItems: { containerId, idPrefix: 'bfast', placeholder } }`) consumed by one generic set of functions — `window.addFreeItem(listKey)`, `renderFreeItemsList(listKey)`, `window.toggleFreeItemQty(listKey, id)`, `window.updateFreeItemData(listKey, id, field, value)`, `window.adjustFreeItemCount(listKey, id, amount)`, `window.removeFreeItem(listKey, id)` — where `listKey` (`'customIngredients'` or `'breakfastItems'`) is baked into the inline `onclick`/`onchange` handlers at render time. `idPrefix` keeps generated element ids/classes (and item ids, e.g. `bfast-172...`) from colliding between the two lists rendered side by side. If you ever need a third free-item list, add an entry to `FREE_ITEM_LISTS` rather than writing new CRUD functions.
  - `computeCalendarDishCounts(assignments)` flattens *only* day assignments (midi/soir — breakfast is no longer dish-based) into a `dishCounts` map consumed by `window.buildShoppingListItems` (see `shoppingList.js`) in `generateCalendarShoppingList()`, which separately concatenates `cal.customIngredients` and `cal.breakfastItems` (the latter tagged with `originLabel: 'Petit-déjeuner'` at call time, undoing on the copy, not the stored item) into that function's `customIngredientsList` argument.
  - `dishNameById(cal, id)` and the shopping-list `dishLookup` both check live `window.dishes` first, falling back to `cal.dishesSnapshot[id]` — **don't drop the fallback in either place**: a calendar can display/generate correctly for dishes the current browser doesn't have (an imported calendar), and skipping the snapshot fallback silently shows "(plat supprimé)" or drops the ingredient even though the dish is fine, just not local. This exact regression happened once when the week view was introduced (`dishNameById` initially only checked `window.dishes`) and was only caught by the share/import Playwright test.
  - Every mutation to the active calendar's *day assignments* goes through `touchActiveCalendar()`, which recomputes `cal.dishesSnapshot` (from `cal.assignments` only, via `snapshotDishesForCalendar(assignments)`) against the *current* `window.dishes` and persists — keeping the snapshot fresh continuously (there's no explicit save step). Free-item edits call `saveLocalData()` directly instead, since they don't affect the dish snapshot (they aren't dishes).
- **`js/calendarShare.js`** — QR/link export+import for a single calendar entry (mirrors `share.js`'s pattern but with its own `?importCalendar=` param so it can't collide with recipe-only share links). `shareCalendarEntry(entry)` bundles `{ name, assignments, breakfastItems, dishesSnapshot }` — the dish snapshot, not live `window.dishes` — so an imported calendar is self-contained even if the recipient lacks those recipes (`cal.customIngredients` is deliberately *not* shared, same as before — only breakfast items took over that `b` payload key when they stopped being dish-based). `checkURLForCalendarImport()` (called from `main.js`) offers to add the parsed calendar into `window.savedCalendars` (tagged `origin: 'imported'`); accepting it also makes it the active calendar and navigates straight to `view-calendar` so the import is immediately visible/usable.
- **`js/main.js`** — entry point; `window.onload` calls `loadLocalData()`, `checkURLForImport()`, then `checkURLForCalendarImport()`. Also listens for `visibilitychange` (and `pageshow` with `event.persisted`, iOS's bfcache-restore signal) to re-run `loadLocalData()` and re-render the current view on resume — a standalone app added to the iOS home screen is typically suspended rather than unloaded in the background, so without this, reopening it after editing data in a different tab/window of the same origin would keep showing the stale in-memory state from before it was backgrounded instead of picking up the change.

**Install to home screen (PWA-lite, no service worker)** — `public/index.html`'s `<head>` wires up `public/manifest.webmanifest` plus `apple-touch-icon`/`theme-color`/`apple-mobile-web-app-*` meta tags so the app can be added to the home screen (iOS 15+ via Safari's share sheet, Android/Chrome via the install prompt) and reopened in `display: standalone` (no browser chrome/URL bar), matching the portal's other apps (e.g. `apps.home.ithasu.org`). There's deliberately no service worker/offline cache — this is icon + fullscreen presentation only, not an installable offline app. `apple-mobile-web-app-status-bar-style` is `black-translucent` (status bar overlays the page instead of reserving its own opaque strip), which only looks right paired with `viewport-fit=cover` on the `<meta name="viewport">` tag and `env(safe-area-inset-top/bottom)` padding on the fixed `header` and `.fixed-footer` (`public/css/style.css`) — without both, the header/footer render underneath the status bar/home-indicator on notched iPhones in standalone mode. Keep that triplet (viewport-fit, header inset, footer inset) together if either fixed bar's CSS changes. The icon itself (blue shopping cart on white, see `public/icons/icon-*.png` and `public/favicon.ico`) is generated by `scripts/generate-icons.sh` (ImageMagick draw primitives, not an SVG source — the container's ImageMagick has no `rsvg-convert`, so its internal SVG renderer silently drops path arcs; redraw by editing that script, not by hand-editing the PNGs). `tests/pwa.spec.js` checks the meta/manifest tags are present and that every file they reference actually resolves (catches a renamed/missing icon file, not real "Add to Home Screen" behavior, which Playwright can't drive).

**Layout:** `main` (the scroll container) spans the full viewport width; the 500px-max, centered content column is applied to `.view-section` instead. Keep it that way — if the width cap moves back onto `main`, touch/drag/scroll gestures started outside that centered column (e.g. the side margins on a wide/landscape screen) stop scrolling anything, because `body` has `overflow: hidden` and isn't a scroll container.

### Data model

A dish: `{ id: string, name: string, ingredients: [{ n: string, q: string }], categoryId: string | null }` (`n` = ingredient name, `q` = optional quantity/weight as free text; `categoryId` references `window.categories`, `null`/absent = uncategorized — old dishes saved before categories existed have no `categoryId` and must keep working, so treat it as optional everywhere). Dishes have no "type" — every dish is eligible for the calendar's midi/soir picker, and none of them are breakfast items (see `js/calendar.js`); a dish may still carry a stale, unused `mealType` field from before this was removed — ignore it, don't read it anywhere.

A category/tab: `{ id, name }`.

A "free item" (dish-independent, name + optional qty + count): `{ id, name, qty, hasQty, count }` — used for both `cal.customIngredients` ("Ingrédients isolés") and `cal.breakfastItems` ("Petits-déjeuners de la semaine"), see below and `js/calendar.js`'s `FREE_ITEM_LISTS`. Neither lives as its own top-level state; both are scoped to a single calendar.

A final shopping list item: `{ id, name, qty, totalCount, origins: string[] }` where `origins` lists which dishes (or "Ajout direct" / "Petit-déjeuner" for free items, see `js/shoppingList.js`'s `originLabel`) contributed to that line.

A calendar (`window.savedCalendars` entry — every calendar lives in this one array, whether it's the one currently open or not): `{ id, name, createdAt, origin: 'local' | 'imported', assignments: { [dateKey]: { midi: [dishId,...], soir: [dishId,...] } }, breakfastItems: [{ id, name, qty, hasQty, count }], customIngredients: [{ id, name, qty, hasQty, count }], dishesSnapshot: { [dishId]: { name, ingredients } } }`. `window.activeCalendarId` names which entry's `id` is currently being edited/viewed in `view-calendar`; it can be `null` (no calendar open yet) or point at an id no longer present (after a delete — handled gracefully, not an invariant to maintain). A calendar saved before `breakfastItems` existed may still carry a stale `breakfastSelection: { [dishId]: count }` field — see `js/storage.js`'s `migrateCalendarBreakfastSelections()`, which converts it once on load; don't read `breakfastSelection` anywhere else.

### Conventions to preserve

- All UI strings are in French; keep new strings consistent with that.
- Functions intended to be called from inline `onclick="..."` handlers in HTML must be attached to `window` (e.g. `window.saveDish = function () {...}`); helper functions only used within their own file can stay as plain `function`.
- IDs for new entities follow ad hoc string schemes (e.g. `String(Date.now())` for dishes, `'cust-' + Date.now() + ...` / `'bfast-' + Date.now() + ...` for the two free-item lists, `'final-' + Math.random()...` for shopping list items, `'cat-' + Date.now()` for categories, `'cal-' + Date.now()` for saved calendars) — match the existing pattern for the relevant collection rather than introducing a new ID scheme.
- Every new user-facing flow should get an accompanying Playwright spec in `tests/` (see Testing above) — this app has no other safety net (no compiler, no unit tests on the DOM-coupled logic).
